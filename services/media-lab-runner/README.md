# Norva Media Lab runner

This service is a private QA boundary for the fixed eleven-case MKV corpus. It
does not accept provider URLs, source/account identifiers, strategy overrides,
or arbitrary fixture paths. The only run request is:

```json
{ "protocol": 1, "fixtureId": "h264-closed-aac" }
```

`POST`, `GET`, and `DELETE /v1/current` require the dedicated
`MEDIA_LAB_RUNNER_TOKEN` bearer token (minimum 32 characters) plus the
Edge-derived, opaque `X-Norva-Lab-Actor` digest. `POST` starts asynchronously,
`GET` returns only `idle|busy|running|complete`, and `DELETE` cancels the
caller's active run. `GET /health` requires the bearer token. Provider media is
served from capability URLs created only for an active run. Every response is
`no-store`, and the public result projection contains only bounded media
metrics. It never includes provider URLs, capability/run IDs, paths, secrets,
or raw errors.

The runner owns one non-queued mono-slot. A concurrent start returns HTTP 409
with the bounded `busy` state. The first simulated HTTP 458 is counted and any retry
makes the physical result fail. Range requests, ETag strength, provider delay,
GET concurrency, bytes and 458 responses are measured by the simulator rather
than accepted from the execution adapter.

Local tests may attach a strictly validated provider scenario directly to the
simulator. This internal-only control can shape initial latency and sustained
bandwidth, emit a bounded sequence of `407`, `408`, `429`, `458`, or `5xx`
responses, and cut a configured number of bodies after an exact byte count.
These controls are never accepted by the runner's HTTP API, so the deployed
eleven-case corpus remains fixed and cannot become an arbitrary provider relay.

The local shared-cache lab also includes a private file-backed R2 simulator. It
provides immutable, immediately readable objects, deterministic availability
failures, and manifest-last publication. Its multi-tenant model stores one HLS
graph globally while keeping source visibility and variant bindings separate;
disabling one tenant's source denies that tenant without removing another
tenant's authorized access. This is a test boundary only and does not make the
production cache shared by itself.

The preferred deployment co-locates the physical executor with this runner.
Set `MEDIA_LAB_GATEWAY_URL`, `MEDIA_LAB_GATEWAY_TOKEN`,
`MEDIA_LAB_CHROMIUM_EXECUTABLE_PATH`, and `MEDIA_LAB_HLS_JS_PATH`; the runner
then creates the dedicated Gateway session itself, drives hls.js in headless
Chromium, verifies decoded audio, seek, rebuffering, and deletes/readbacks the
session. The included Dockerfile installs Chromium and copies the pinned hls.js
asset. A remote executor remains possible with the mutually-exclusive
`MEDIA_LAB_PHYSICAL_ADAPTER_URL` and `MEDIA_LAB_PHYSICAL_ADAPTER_TOKEN` pair.
Without either complete configuration the service returns
`blocked/dedicated-gateway-unavailable`.

H.264 fixtures first complete a training session so the Gateway can produce its
full-file IDR/timestamp proof; only the following session is measured. The
provider simulator independently counts both sessions and still enforces a
single concurrent GET. The HEVC complete-cache case performs one real cold seed
through the dedicated Gateway, waits for complete EOF promotion and cleanup,
then resets only the simulator's counters before measuring the same immutable
fixture again. That measured opening passes only when the Gateway reports a
complete-cache hit with zero provider GET and zero FFmpeg spawn; the runner
never fabricates a cache artifact or cache hit. A `pass` is impossible without
Gateway, browser and cleanup attestations plus fixture-specific counter gates.
The terminal-458 case intentionally never launches a browser.

The production Docker build generates the pinned fixture corpus in an isolated
builder stage. It synthesizes the PGS seed with the Gateway's existing parser,
round-trips its two bitmap cues, then runs the exact FFmpeg plan. Before a file
can enter `fixture-lock.json`, a fail-closed ffprobe/FFmpeg gate verifies its
actual stream graph, codecs, profiles, dimensions, frame rate, subtitle type,
packet timestamps and H.264 IDR/open-vs-closed GOP property. The final runner
image receives only the verified corpus and Chromium; it does not need the
fixture-building toolchain at runtime.

For a manual development generation, use:

```powershell
npm run fixtures:plan
$env:MEDIA_LAB_FFMPEG_PATH = 'C:\\tools\\ffmpeg.exe'
$env:MEDIA_LAB_FFPROBE_PATH = 'C:\\tools\\ffprobe.exe'
npm run fixtures:generate
```

The PGS seed is generated by `scripts/generate-pgs-seed.py`; it is never fetched
from a third party. The defective-timestamp file is admitted only when the
post-generation packet scan observes the intended non-strict DTS sequence. The
complete-cache case is seeded only through the dedicated Gateway. Both facts
are explicit gates rather than inferred from recipe names.
